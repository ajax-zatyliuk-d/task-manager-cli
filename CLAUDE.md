# Навчальний проєкт: C та GLib

Працюй українською як наставник і рев’юер. Мета користувача — самостійно
написати код, зрозуміти рішення та вміти пояснити їх техліду.
Правила взаємодії: `.claude/rules/mentoring.md`.

## Вимоги та межі проєкту

- Однопоточний консольний менеджер задач на C, GLib >= 2.56.
- Джерело вимог: `docs/glib-containers-task.pdf`. Якщо файл перемістили,
  спочатку знайди його. Вимоги PDF відрізняй від інструкцій користувача.
- Узгоджену архітектуру описано нижче; це вибір із дозволених PDF варіантів.
- Без глобального стану. `TaskManager` видає ID та узгоджує всі індекси.
- `Task` у базовій версії — звичайна структура C, не GObject.
- CLI читає команди, викликає менеджер і друкує результати та помилки.
- Структура: `src/` (бібліотека `task_manager_core`: `task`, `task_manager`,
  `cli`), `main.c` (застосунок), `tests/` (g_test), `docs/` (вимоги PDF).
- GObject, GMainLoop і робочий потік — окремий навчальний етап. Додавай
  їх лише за потреби.

## Узгоджена архітектура та володіння

`Task`: `guint id`, `gchar *title`, `gint priority` (1..10),
`GPtrArray *tags`, `gint64 created_at` від `g_get_monotonic_time()`.
Задача володіє копією назви, масивом тегів і власними рядками тегів.
Створена без тегів задача має існуючий порожній масив (`len == 0`).

| Поле менеджера | Вміст та володіння |
| --- | --- |
| `tasks_by_id` | `GHashTable`: ID -> `Task *`. Єдиний власник задач. ID кодуються через `GUINT_TO_POINTER()`, використовуються `g_direct_hash` / `g_direct_equal`. Ключі не звільняються. Очищення значення викликає `task_free()`. |
| `tasks_by_tag` | `GHashTable`: власна копія рядка тегу -> власний `GPtrArray` з позиченими `Task *` (без free-функції елементів, задачами володіє лише `tasks_by_id`). Масив створюється через `g_ptr_array_new()`, очищення значення — `g_ptr_array_free(arr, TRUE)`. Задача має бути прибрана з масиву до звільнення, інакше вказівник висітиме. |
| `unique_tags` | `GHashTable` як множина через `g_hash_table_add()`. Власні копії рядків тегів, які використовує хоча б одна задача. Ключ звільняється один раз, очищення значення — `NULL`. |
| `tasks_sorted` | `GSequence` з позиченими `Task *`, без звільнення задач. Більший пріоритет першим, потім старіша задача, потім менший ID. `top n` читає перші n елементів. |
| `run_queue` | `GQueue` з позиченими `Task *` у порядку `enqueue` (як і в `tasks_by_tag`, `tasks_sorted`). Одну задачу можна поставити в чергу кілька разів. Назва або теги не змінюють місце задачі у FIFO. Задачами не володіє; `g_queue_free` елементи не звільняє. |
| `history` | Окрема `GQueue`, яка володіє копіями останніх 10 команд. Одинадцята витісняє та звільняє найстарішу. |

Таблиці з рядковими ключами використовують `g_str_hash` / `g_str_equal`.
Рядки одного тегу в задачі, індексі та множині мають незалежних власників.
Для callback очищення використовуй коректну сигнатуру `GDestroyNotify`;
приватна функція-адаптер уже застосована для `task_free()`.

Обґрунтування `tasks_by_tag`: PDF вимагає `GHashTable<string, GPtrArray*>`
або `GList*` для списку завдань. `GArray` з ID не входить до цих варіантів,
тому значення — `GPtrArray` з позиченими `Task *`: `find` читає задачі
без додаткового пошуку. Ціна — той самий порядок видалення, що й для
`tasks_sorted` (див. нижче). Раніше розглядався варіант з ID через
`GUINT_TO_POINTER()`; відхилено, бо це вимагало б окремого пошуку в
`tasks_by_id` без вигоди для навчальної мети.

`unique_tags` логічно дублює ключі непорожнього `tasks_by_tag`. Це свідомо
залишено через вимогу PDF продемонструвати множину; не подавай її як
необхідну оптимізацію пошуку та не прибирай без обговорення.

При видаленні задачі спочатку прибери її з індексу тегів, послідовності
та черги (усі входження), поки `Task` ще живий. Порожній масив задач тегу
означає видалення тегу з індексу та множини. Запис із `tasks_by_id`
видаляється ОСТАННІМ — це звільняє задачу. Перед цим ми очищуємо записи
посилань на таску за допомогою `task_manager_unindex_task()`; нею користуються
і `del`, і `run`. `run` бере задачу з голови черги, робить `g_hash_table_steal()`
і очищає `tasks_by_id` від посилання на цю задачу; викликач отримує 
володіння та звільняє об'єкт через `task_free()`.

## API та контракти

- Використовуй наявні назви `task_manager_*`; не перейменовуй їх заради
  прикладів `tm_*` з PDF. `TaskManager` — непрозорий тип у заголовку.
- `task_manager_add_task()` копіює назву, повертає ID від 1; неправильний
  пріоритет дає 0 та `TM_ERROR_INVALID_PRIORITY`, без зміни стану.
  Менеджер сам створює задачі, видає ID від 1 до `G_MAXUINT - 1` і
  володіє ними до видалення або передачі через `run`. Лічильник зростає
  тільки після успішного додавання; видалені ID не використовуються повторно.
  Вичерпання ID дає `TM_ERROR_ID_EXHAUSTED` до перевірки полів задачі.
- `Task` можна створити, змінити та звільнити незалежно від менеджера.
  Поки задача належить менеджеру, позичені вказівники доступні лише для
  читання: прямі зміни обійшли б індекси та порядок менеджера.
- `task_manager_find_task_by_id()` повертає позичений `const Task *`; невідомий
  ID дає `NULL` та `TM_ERROR_TASK_NOT_FOUND`. Знайдену задачу не звільняють.
- Параметр `GError **error` може бути `NULL`. Коли його передають,
  змінна викликача має тип `GError *` і початкове значення `NULL`.
  Встановлення помилки не замінює необхідне повернення з функції.
- Для наявних операцій ненульові `manager` та `title` — погоджені
  передумови. `task_manager_free(NULL)` дозволений;
  `task_free(NULL)` поки не підтримується.
- Теги: без `#`, непорожній рядок з `[a-z0-9_]`. Недопустимий тег
  відхиляється з `TM_ERROR_INVALID_TAG`, а не нормалізується.
  `task_manager_tag_task()`: тег, який задача вже має, — `FALSE` та
  `TM_ERROR_DUPLICATE_TAG` без змін стану (вимога 4 PDF). `add` з повтором
  тегу в одній команді дає ту саму помилку без додавання задачі в колекцію.
  `task_manager_untag_task()` для відсутнього тегу — тихий `TRUE`.
  Невідомий ID дає `TM_ERROR_TASK_NOT_FOUND`. `FALSE` супроводжується
  `GError`, якщо викликач передав ненульовий `error`.
- Дозволено `g_autoptr` / `g_autofree` / `g_auto` (GCC/Clang, GLib ≥ 2.44);
  для `TaskManager` є `G_DEFINE_AUTOPTR_CLEANUP_FUNC`. Повернення
  такого значення з функції — лише через `g_steal_pointer()`.
- `task_manager_find_tasks_by_tag()` повертає `GPtrArray *` (без `const`).
  Валідний тег завжди дає новий масив; якщо збігів немає, `len == 0`.
  Недопустимий тег — `NULL` та `TM_ERROR_INVALID_TAG`. Викликач володіє
  масивом і звільняє його через `g_ptr_array_unref()`, також порожній
  результат. Елементи — позичені `Task *`: ними володіє менеджер, і після
  видалення задачі відповідні вказівники недійсні. Масив є копією
  вказівників, тож зміна його складу не чіпає внутрішній індекс.
- `task_manager_top_tasks(n)` повертає новий `GPtrArray` з позиченими
  `Task *` (викликач звільняє масив, не задачі); `n == 0` дає порожній масив.
- `task_manager_enqueue_task()`: невідомий ID — `TM_ERROR_TASK_NOT_FOUND`,
  дубль у черзі дозволений. `task_manager_run_next()` на порожній черзі
  повертає `NULL` без помилки.
- `task_manager_remove_task()`: невідомий ID — `TM_ERROR_TASK_NOT_FOUND`.
- Історія: CLI викликає `task_manager_record_command()` для кожного
  непорожнього рядка ДО виконання, також невдалих і невідомих команд.
  Не записуються `quit` і `history` (рішення користувача 2026-11-18:
  перегляд історії її не засмічує). Менеджер ігнорує порожній рядок, володіє
  копіями останніх 10 (приватна константа) і витісняє найстарішу.
  `task_manager_get_history()` повертає новий `GPtrArray` з копіями рядків
  (від найстарішої), викликач звільняє через `g_ptr_array_unref()`.
- `task_manager_get_stats()` повертає `TaskManagerStats` за значенням:
  `tasks`, `unique_tags`, `queue_length` (записи черги, з дублями).
- CLI (`src/cli.c`): `cli_execute_line(manager, line, output, error)`.
  Успішний вивід — у `GString` з кінцевим `\n`; помилки — лише через
  `GError` без `\n` (`CLI_ERROR_USAGE`, `CLI_ERROR_UNKNOWN_COMMAND`;
  помилки менеджера передаються без обгортки); `quit` дає `CLI_QUIT`.
  Команди в таблиці `commands[]`; кількість аргументів точна; ID — це
  `1..G_MAXUINT`; тег у `tag`/`untag`/`add`/`find` задається з `#`,
  менеджеру передається без нього. Помилки друкує `main` через
  `g_printerr("error: ...")`.

## Збірка

Система збірки — CMake з пресетами (`CMakeLists.txt`, `CMakePresets.json`);
Makefile прибрано. Стиль запозичено з проєкту mcu_communicator
(`CLAUDE_REFERENCE.md` — лише довідка, не опис цього проєкту).

```bash
sudo apt install cmake pkg-config libglib2.0-dev clang-format valgrind
```

```bash
cmake --preset debug                      # configure: ASan + UBSan
cmake --build --preset debug -- -j$(nproc)
ctest --preset debug                      # усі тести
```

Каталоги збірки лежать поруч із репозиторієм:
`../task-manager-cli-<preset>/out/bin/` (застосунок `task_manager` і три
тестові програми). У репозиторії збірок немає.

| Пресет | Що | Навіщо |
| --- | --- | --- |
| `debug` | `Debug`, `ENABLE_SAN=ON` (ASan + UBSan, UB не відновлюється) | щоденна розробка; витік чи UB валить тест |
| `release` | `RelWithDebInfo`, без санітайзерів | valgrind (не поєднується з ASan) |

`autobuild.sh` обгортає ці команди:

```bash
./autobuild.sh                    # build debug (configure за потреби)
./autobuild.sh configure|build|test|clean [debug|release]
./autobuild.sh valgrind           # усі тести під valgrind (release)
./autobuild.sh format             # clang-format -i для всіх *.c/*.h
./autobuild.sh format-check       # перевірка без змін; код 1 при порушеннях
```

Параметри CMake: C11 з GNU-розширеннями (потрібні для `g_autoptr`),
`-Wall -Wextra -Werror`, GLib >= 2.56 через `pkg_check_modules`.
Бібліотека `task_manager_core` (`src/*.c`) лінкується до застосунку та
тестів. Кожен файл `tests/*.c` має власний `main()` і є окремим
виконуваним файлом та окремим тестом CTest; не компонувати їх разом.
Новий вихідний файл додавай у `task_manager_core`, нову тестову
програму — у список `foreach` у `CMakeLists.txt`.

## Стиль коду

- Правила — `.clang-format` (база Google, змінена; з mcu_communicator).
- Ширина рядка 140, відступ 4 пробіли без табуляцій.
- Дужки: `BreakBeforeBraces: Mozilla` — для функцій і `struct`/`enum`
  `{` на новому рядку, для `if`/`for`/`while`/`switch` на тому ж рядку.
- `PointerAlignment: Left` (`Task* task`), але в конфігурації ввімкнено
  `DerivePointerAlignment: true`: clang-format бере переважний стиль файлу,
  тож наявний `Task *task` лишиться. Для справжнього Left треба вимкнути
  Derive — це окреме рішення.
- `case` з відступом усередині `switch`; `SortIncludes: false`.
- Перед комітом: `./autobuild.sh format-check`; виправлення —
  `./autobuild.sh format`. Масове переформатування робити окремим
  комітом, не змішуючи з логікою.

## Тести

- Фреймворк — GLib `g_test_*` (вимога PDF). У mcu_communicator — CMocka;
  на нього не переходити без окремого рішення.
- Пам'ять: `debug` ловить витоки через ASan/LSan (тест падає з ненульовим
  кодом); `./autobuild.sh valgrind` перевіряє `release`-збірку.
- Окремий тест: `../task-manager-cli-debug/out/bin/test_cli -p /cli/add`.

### Покриття

Тести додаються разом із поведінкою. PDF вимагає сценаріїв: додавання та
пошук за ID; пошук за тегом після untag; порядок top при рівних
пріоритетах; del задачі в черзі; витіснення першої з 11 команд історії.
Усі п'ять покрито (історія — у `test_task_manager`). Автоматичні ID ростуть
у порядку створення; при рівних часових позначках порядок визначає ID.
Перед кожною здачею: `./autobuild.sh test` (debug з ASan),
`./autobuild.sh valgrind` і `./autobuild.sh format-check`; перевіряй код
виходу. Не фільтруй вивід збірки чи тестів через `grep`: це ховає падіння.

Статус: базова версія за PDF завершена — бібліотека, усі команди CLI,
застосунок `task_manager`.
