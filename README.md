# Менеджер завдань на C та GLib

Навчальний проєкт з онбордингу для практики з контейнерами GLib. Менеджер зберігає задачі з пріоритетами й тегами, підтримує чергу виконання та історію команд. Консольний застосунок читає команди зі стандартного вводу. Вихідні вимоги описано в [завданні](docs/glib-containers-task.pdf).

## Збірка й запуск

Потрібні Linux, GCC або Clang, CMake 3.25+ для пресетів, `pkg-config` і GLib 2.56+ із заголовками. На Debian або Ubuntu базові залежності можна встановити так:

```sh
sudo apt install build-essential cmake pkg-config libglib2.0-dev
```

З кореня репозиторію:

```sh
bash ./autobuild.sh build debug
../task-manager-cli-debug/out/bin/task_manager
```

Назва каталогу збірки залежить від назви каталогу репозиторію. Якщо репозиторій називається `task-manager-cli`, бінарники лежать у `../task-manager-cli-<preset>/out/bin/`.

| Пресет | Тип збірки | Призначення |
| --- | --- | --- |
| `debug` | `Debug`, `ENABLE_SAN=ON` | Розробка й тести з ASan та UBSan |
| `release` | `RelWithDebInfo`, `ENABLE_SAN=OFF` | Оптимізована збірка з налагоджувальними символами для Valgrind |

Проєкт збирається як C11 із GNU-розширеннями та прапорцями `-Wall -Wextra -Werror`. Для ручної конфігурації та збірки можна викликати `cmake --preset debug` і `cmake --build --preset debug --parallel`.

## Команди CLI

```sh
printf '%s\n' 'add 5 buy milk #home' 'find #home' 'enqueue 1' 'run' 'stats' 'quit' \
    | ../task-manager-cli-debug/out/bin/task_manager
```

| Команда | Дія |
| --- | --- |
| `add <priority> <title> [#tag ...]` | Створює задачу й виводить її ID. Пріоритет від 1 до 10 |
| `del <id>` | Видаляє задачу |
| `tag <id> <#tag>` / `untag <id> <#tag>` | Додає або прибирає тег задачі |
| `find <#tag>` | Виводить задачі з указаним тегом, наприклад `id: 1, priority: 5, title: buy milk` |
| `top <n>` | Виводить до `n` задач за спаданням пріоритету |
| `enqueue <id>` | Ставить задачу в кінець черги виконання |
| `run` | Виконує наступну задачу з черги й видаляє її з менеджера |
| `history` | Виводить останні 10 записаних команд від найстарішої до найновішої |
| `stats` | Виводить кількість задач, унікальних тегів і записів у черзі |
| `quit` | Завершує сесію |

Тег має бути непорожнім і складатися із символів `[a-z0-9_]`. У CLI йому передує `#`. Повторний тег для тієї самої задачі дає `TASK_ERROR_DUPLICATE_TAG` у API `Task` та `TM_ERROR_DUPLICATE_TAG` у API менеджера; CLI показує текст помилки. `add` із повтором тегу відхиляється без додавання задачі до менеджера.

Результати команд ідуть у stdout, помилки — у stderr із префіксом `error:`. Сесію можна завершити командою `quit` або кінцем вводу. Історія містить також невдалі команди, крім рядків із першим токеном `history` (наприклад, `history extra`). Точна команда `quit` також не записується; `quit extra` записується як невідома команда.

## Тести, пам’ять і форматування

```sh
bash ./autobuild.sh test debug
bash ./autobuild.sh valgrind
bash ./autobuild.sh format-check
bash ./autobuild.sh format
```

`test debug` збирає проєкт і запускає CTest із ASan та UBSan. `valgrind` збирає пресет `release` і запускає під Valgrind усі три тестові програми. Для цих перевірок окремо встанови `valgrind` і `clang-format`. CI використовує `clang-format` 18.1.3. Команда `format` перезаписує вихідні файли, а `format-check` лише перевіряє їх.

Окремий тест GLib після збірки можна запустити так:

```sh
../task-manager-cli-debug/out/bin/test_task_manager -p /task-manager/untag/valid
```

У GitHub Actions окремо перевіряються тести з ASan та UBSan, тести під Valgrind і форматування.

## Структура

| Шлях | Призначення |
| --- | --- |
| `main.c` | Читає stdin, викликає обробник CLI та виводить результати |
| `src/task.[ch]` | Створення й звільнення задач, доступ до їхніх полів і зміна тегів |
| `src/task_manager.[ch]` | Менеджер, індекси, черга та історія |
| `src/cli.[ch]` | Розбір і виконання команд |
| `tests/` | Окремі програми `test_task`, `test_task_manager` і `test_cli` |
| `CMakeLists.txt`, `CMakePresets.json`, `autobuild.sh` | Конфігурація збірки, пресети й команди розробки |

CMake збирає код із `src/` у статичну бібліотеку `task_manager_core`, яку використовують застосунок і тести.

## Контейнери й володіння

| Контейнер | Роль |
| --- | --- |
| `tasks_by_id` (`GHashTable`) | Пошук за ID. Таблиця володіє задачами |
| `tasks_by_tag` (`GHashTable` → `GPtrArray`) | Пошук за тегом. Таблиця володіє ключами й масивами. Масиви позичають `Task *` |
| `unique_tags` (`GHashTable` як множина) | Облік унікальних тегів |
| `tasks_sorted` (`GSequence`) | Порядок для `top`: вищий пріоритет, старіша задача, менший ID |
| `run_queue` (`GQueue`) | FIFO-черга з позиченими `Task *` |
| `command_history` (`GQueue`) | Черга, що володіє копіями останніх 10 команд |
| `Task.tags` (`GPtrArray`) | Масив, що володіє рядками тегів задачі |

Під час видалення задачі менеджер спочатку прибирає її з індексів і черги, а потім звільняє через `tasks_by_id`.

Публічні API описано в [`src/task.h`](src/task.h) і [`src/task_manager.h`](src/task_manager.h). Самостійно створеною задачею володіє викликач і звільняє її через `task_free()`. `Task` перевіряє діапазон пріоритету, формат тегів і їхню унікальність у задачі. Менеджер надає наявні коди `TM_ERROR_*` для помилок цих перевірок.

`task_new_with_tags()` створює самостійну задачу з початковими тегами. Масив і його рядки залишаються у власності викликача; задача зберігає копії. `NULL` або порожній масив означає відсутність тегів. При помилці конструктор повертає `NULL` і звільняє частково створену задачу. `task_new()` створює задачу без тегів.

`task_manager_take_task()` приймає вже створену задачу з ID від 1 до `G_MAXUINT - 1`. У разі успіху менеджер стає власником, а викликач більше не змінює й не звільняє задачу. При помилці, зокрема конфлікті ID, задача залишається у власності викликача, а менеджер не змінюється. Автоматичне призначення ID пропускає вже зайняті ID.

Пошук за ID повертає позичений `const Task *`. Пошук за тегом і `top` повертають новий `GPtrArray` із позиченими задачами; викликач звільняє лише масив через `g_ptr_array_unref()`. Задачі, якими володіє менеджер, доступні лише для читання: пряма зміна тегів або пріоритету обходить індекси менеджера. Для зміни пріоритету використовуй `task_manager_set_task_priority()`: менеджер перевіряє його через `Task` і оновлює порядок; при помилці стан не змінюється. Вказівники в масиві дійсні, доки менеджер володіє відповідною задачею; масив не оновлюється після її видалення чи вилучення через `run`.

Для валідного тегу без збігів пошук повертає порожній масив, для некоректного — `NULL` і `TM_ERROR_INVALID_TAG`, якщо передано `GError **`. `task_manager_run_next()` вилучає оригінальну задачу з менеджера та передає володіння викликачу, який звільняє її через `task_free()`. Масив історії та копії його рядків звільняються через `g_ptr_array_unref()`.

Менеджер працює в одному потоці. Самостійній задачі ID задає викликач; автоматичні ID менеджера призначаються від 1 до `G_MAXUINT - 1`. Лічильник просувається лише після успішного автоматичного додавання; помилка валідації його не змінює. Після вичерпання додавання повертає 0 і `TM_ERROR_ID_EXHAUSTED` за наявності `GError **`, не змінюючи колекцію.
