Скопіюй цей блок у Claude Code, відкритий у корені проєкту:

```text

Код пишу я. Не редагуй файли й не пиши реалізацію без мого прямого
прохання про конкретну зміну. «Перевір», «далі» і «+» означають рев’ю
або продовження навчання, а не дозвіл писати код за мене.

Спочатку прочитай CLAUDE.md, .claude/rules/mentoring.md,
.claude/handoff.md та docs/glib-containers-task.pdf.
Переглянь фактичні файли src/, tests/, Makefile і main.c.

Проведи рев’ю поточної реалізації: make -B test (перевір код виходу, не
фільтруй вивід), valgrind --leak-check=full та, за потреби, ASan.
Спочатку поведінка, володіння пам’яттю, GError та зміст тестів. Для
кожної проблеми — файл/рядок, сценарій і пояснення. Файли не змінюй.

Якщо суттєвих проблем немає, переходь до історії команд: спершу
узгодь контракт (див. нижче), потім дай одне посильне завдання.
```

## Прийняті рішення, які легко забути

- Теги без `#`, лише `[a-z0-9_]`, недопустимі відхиляються (не нормалізуються).
- Повторний tag і untag відсутнього тегу — тихий `TRUE`.
- `find` за відсутнім тегом — `NULL` без помилки; масив чинний до наступної
  зміни менеджера.
- Дублікати в `run_queue` дозволені; порожня черга для `run` — `NULL`
  без помилки; `run` повертає копію `Task`, яку звільняють `task_free()`.
- `tasks_by_tag` та `run_queue` тримають `Task *`, а не ID (рішення
  користувача заради відповідності PDF; див. обґрунтування в CLAUDE.md).

## Наступне: історія команд

Контракт ще треба узгодити (одне завдання за раз, без реалізації):
1. Хто записує команди: `task_manager_record_command(manager, command)`.
2. Чи записувати невдалі команди та саму `history`.
3. Читання: новий `GPtrArray` з копіями (від найстарішої до найновішої)
   чи позичений `const GQueue *`.
4. Константа розміру (10), порожній рядок.
5. Володіння: `g_strdup` при додаванні, `g_free` при витісненні,
   знищення через `g_queue_free_full(queue, g_free)`.

Тест за PDF: 11 команд → в історії 10, перша витіснена.

## Питання для незалежного рев’ю

Граничні випадки видачі ID та переповнення `guint`; час життя позичених
результатів; чи тести справді перевіряють обіцяну поведінку (порядок за
`created_at` через публічний API не відрізнити від порядку за ID);
контрактні коментарі в `task_manager.h` короткі й місцями неповні.
